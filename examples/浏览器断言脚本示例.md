# 浏览器断言脚本示例

菜谱关键字 **`断言`**（对标 `脚本`），在设置 → **断言脚本** 中编写。专供测试工程师做页面验收。

> **开启方式**：设置 → 帮助 → 连续点击版本号 **6 次**即开启断言能力（可在「通用」中关闭）。普通用户默认不可见该入口。

## 与「脚本」的区别

| | `脚本`（业务 Rhai） | `断言`（本体系） |
|--|--|--|
| 能力 | 本机 Excel / ZIP / 文件 | **浏览器** XPath / URL / 标题 |
| 是否要浏览器 | 否 | **是**（先 `打开`/`登录`） |
| 失败是否页面恢复 | 否 | **否** |
| XPath | 无 | **仅此处** |

操作步骤仍用 `打开` / `点击` / `等待` / `输入`；验收用 `断言…`。

## 调用

```text
打开https://example.com/login，
输入手机=…，点击登录，
断言检查页面标题 工作台
```

或自定义脚本：`断言我的登录检查`

`ARGS` 为名称后的剩余字符串。

## 宿主 API

| API | 说明 |
|-----|------|
| `ARGS` | 调用参数 |
| `assert_exists(xpath)` / `assert_exists(xpath, timeout_secs)` | 至少 1 个节点 |
| `assert_not_exists(xpath)` / 带超时 | 0 个节点 |
| `assert_visible(xpath)` / 带超时 | 存在且可见 |
| `assert_text(xpath, expected)` / 带超时 | 首节点文本 **包含** expected |
| `assert_attr(xpath, name, expected)` | 属性 trim 后全等 |
| `assert_url_contains` / `assert_url_equals` | `location.href` |
| `assert_title_contains` / `assert_title_equals` | `document.title` |
| `xpath_count` / `xpath_text` / `xpath_attr` | 只读查询 |
| `print` / `throw` | 日志 / 硬失败 |

默认超时约 5 秒；轮询间隔约 200ms。多匹配时断言针对**第一个**节点。

## XPath 使用说明（快速入门）

断言里的定位走浏览器原生 `document.evaluate`，**只在断言脚本中可用**，不会进 `点击`/`等待`/`输入`。

### XPath 是什么？和 JS / Python 有什么关系？

**XPath 是一套独立的「在 HTML/XML 里找节点」的查询语言**（W3C 标准），不是 JavaScript，也不是 Python。

- 你写的是一段 **路径字符串**，例如 `//button[contains(.,'提交')]`
- **Chrome / Selenium / Playwright / 本工具** 都是把这段字符串交给浏览器去解析
- 所以：**同一条 XPath，在 JS、Python、本断言脚本里写法一样**；变的只是「外层怎么调用」

| 环境 | 怎么用同一条 XPath |
|------|-------------------|
| Chrome 控制台 | `$x("//button[contains(.,'提交')]")` |
| Python + Selenium | `driver.find_element(By.XPATH, "//button[contains(.,'提交')]")` |
| JavaScript（页内） | `document.evaluate("//button[...]", document, ...)` |
| 本工具断言脚本 | `assert_exists("//button[contains(.,'提交')]")` |

记住一句即可：**学会 XPath 字符串本身；换语言只是换一层 API 外壳。**

### 为什么推荐写 `//`，而不是 `/html/body/...`？

这是 **XPath 路径规则**，和编程语言无关：

| 前缀 | 含义 | 例子 | 何时用 |
|------|------|------|--------|
| `//` | 从文档**任意位置**往下找（「全文搜索」） | `//button` = 任意深度的 button | **日常首选** |
| `/` | 必须从**当前起点（通常是根）一级级往下** | `/html/body/div[1]/button` | 路径极稳、层级固定时 |

对比直觉：

- `//button` ≈ 「页面里随便哪的 button」→ 页面多包一层 `div` 往往还能找到  
- `/html/body/div/button` ≈ 「必须沿着这条祖宗链」→ 前端一改布局就容易挂  

所以测试里大家默认写 `//…`：稳一点、短一点。绝对路径 `/html/...` 不是错，只是更脆，本说明不推荐新手一上来就用。

`*` 表示任意标签：`//*[@id='loginBtn']` = 「任意标签，只要 id 是 loginBtn」。

### 在断言脚本里怎么写字符串

外层是 Rhai（类似简易 JS），内层是 XPath：

- 外层用双引号包住整段 XPath  
- XPath **里面**的属性/文字用单引号，少转义：

```rhai
assert_exists("//button[contains(.,'提交')]", 10);
assert_attr("//input[@id='phone']", "placeholder", "手机号");
```

### 重要：写在「菜谱」里时，注意 `.` 和 `,`

菜谱默认会把英文句号 `.`、逗号 `,` 当成步骤分隔。  
XPath 常见写法 `contains(.,'查询')` 里同时有 `.`（当前节点）和 `,`（函数参数分隔）——旧版会误拆成非法 XPath。

**现已修复**：括号 `()` / 方括号 `[]` 里的 `.`、`,` 不再拆步，可直接写：

```text
断言元素存在 //button[contains(.,'查询')]
```

若仍异常，可转义：`contains(\.\,'查询')`，或把 XPath 写进「设置 → 断言脚本」正文（不走菜谱拆步），菜谱只写 `断言我的检查`。

### 常用模式（够用就这几条）

| 目的 | 示例 | 读法 |
|------|------|------|
| 按标签 | `//button` | 任意 button |
| 精确属性 | `//*[@id='loginBtn']` | id 等于 loginBtn |
| 属性包含 | `//div[contains(@class,'error')]` | class 里带 error（class 常有多个词） |
| 可见文案包含 | `//button[contains(.,'提交')]` | 按钮文字里带「提交」 |
| 精确文案 | `//button[normalize-space(.)='确定']` | 去掉多余空白后正好是「确定」 |
| 第 N 个 | `(//button[contains(.,'删除')])[1]` | 第 1 个匹配（更稳） |
| 先框范围再找 | `//form[@id='login']//button[@type='submit']` | 登录表单里的提交按钮 |
| 排除 | `//button[contains(.,'提交') and not(@disabled)]` | 提交且未禁用 |

方括号 `[]` = 过滤条件；`.` = 当前节点的文本内容；`@id` / `@class` = 属性。

**空白不敏感**：页面常写成「查 询」。`contains(.,'查询')`、`assert_text`、`assert_title_contains` 会去掉全部空白再比，两边一致即可。

### 与断言 API 的对应关系

| API | XPath 侧实际看什么 |
|-----|-------------------|
| `assert_exists` / `xpath_count` | 匹配节点个数 |
| `assert_visible` | 第一个元素是否可见（非 `display:none` 等，且宽高>0） |
| `assert_text` / `xpath_text` | 第一个节点的文本（去全部空白后 **包含** 判断） |
| `assert_attr` / `xpath_attr` | 第一个元素的属性（trim 后全等） |

`assert_url_*` / `assert_title_*` **不需要** XPath。

### 实践建议（按这个练，上手最快）

1. **先在 Chrome 验证，再贴进脚本**  
   F12 → Console → `$x("//button[contains(.,'提交')]")`  
   返回非空数组再写入 `assert_exists(...)`。
2. **定位优先级**：`id` / `data-*` / 稳定文案 → 再 `contains(@class,…)`；少绑带哈希的长 class。
3. **多匹配要收窄**：引擎默认只看**第一个**；要「恰好 1 个」时自己数：

```rhai
let n = xpath_count("//div[contains(@class,'toast')]");
if n != 1 {
    throw "期望 1 条 toast，实际 " + n;
}
```

4. **等得出来再断言**：动态出现用 `assert_visible(xp, 15)`，别只靠默认 5 秒。
5. **iframe**：断言会扫 **主文档 + 同源 iframe + 跨域 OOPIF**（与点击扇出类似，但仍是断言私有逻辑）。动态 iframe 可加大超时，例如 `assert_exists(xp, 15)`。  
6. **职责分离**：菜谱负责 `打开/点击/输入`；断言脚本只用 XPath **验收**，不要指望在断言里「点击」。

### 5 分钟自测清单

1. 打开目标页，用 `$x("//h1")` 能否列出标题？  
2. 把成功的那条改成 `assert_exists("…")` 放进断言脚本。  
3. 故意写错一个字，确认步骤失败且**不会**刷新页面重试。  
4. 再写一条 `assert_text("//h1", "期望关键字")`。

过完这四步，日常 80% 的页面断言都能写。

### 内置断言脚本（设置 → 断言脚本）

入门优先用这些，ARGS 尽量只填变化部分：

| 菜谱写法 | 覆盖的模式 / API |
|----------|------------------|
| `断言检查页面标题 登录` | 标题包含 |
| `断言标题等于 工作台` | 标题全等 |
| `断言URL含 /dashboard` | URL 包含 |
| `断言URL等于 https://…` | URL 全等 |
| `断言元素存在 //button` | 任意 XPath 存在 |
| `断言元素不存在 //div[contains(@class,'error')]` | 不存在 |
| `断言元素可见 //nav` | 可见 |
| `断言按标签存在 button` | `//button` |
| `断言按ID存在 loginBtn` | `//*[@id='…']` |
| `断言class含 error` | `contains(@class,'…')` |
| `断言按钮含文案 查询` | `//button[contains(.,'…')]`（空白不敏感） |
| `断言精确按钮文案 确定` | `normalize-space(.)='…'` |
| `断言第N个按钮 1` / `断言第N个按钮 2 删除` | `(//button)[n]` |
| `断言表单内提交 login` | 表单内 `type=submit` |
| `断言按钮可点 提交` | 含文案且 `not(@disabled)` |
| `断言文本包含 //h1\|\|\|欢迎` | `assert_text`（`\|\|\|` 分隔） |
| `断言属性等于 //input[@id='phone']\|\|\|placeholder\|\|\|手机号` | `assert_attr` |
| `断言恰好N个 //button\|\|\|3` | `xpath_count` |

## 示例

### 标题

```rhai
/// 用法：断言检查页面标题 登录
let expect = ARGS;
if expect == "" {
    throw "请提供标题关键字";
}
assert_title_contains(expect);
print("标题断言通过");
```

### 元素存在

```rhai
/// 用法：断言元素存在 //button[contains(.,'提交')]
let xp = ARGS;
if xp == "" {
    throw "请提供 XPath";
}
assert_exists(xp, 10);
print("元素存在断言通过");
```

### 组合

```rhai
assert_url_contains("/dashboard");
assert_visible("//nav", 8);
assert_text("//h1", "欢迎");
if xpath_count("//div[contains(@class,'error')]") > 0 {
    throw "页面出现错误提示";
}
print("全部断言通过");
```

## 失败语义

- `throw` 或 API 断言失败 → 本步失败 → **不**刷新重试  
- 执行器会按既有逻辑尝试失败截图  
- 只 `print`、不 `throw`：步骤仍算成功  
- 同一任务内多次 `断言` 写入一份 `documents/断言报告-*.md`；任务结束时在对话日志输出 `[断言报告]…[/断言报告]` 汇总
